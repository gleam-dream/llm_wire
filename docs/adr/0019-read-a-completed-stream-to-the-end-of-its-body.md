# Read a completed stream to the end of its body before delivering the outcome

<a id="adr-0019"></a>

## Decision and alternatives

- The stream owner used to close the HTTP body as soon as the provider's terminal event arrived. When the end of the chunked body followed in a later chunk, HTTP Gun ended the exchange locally: an HTTP Gun recording stored a complete answer with a cut-off ending (`abandoned` when the body was released by its scope or its opener ended, `aborted` with `cancelled` when it was cancelled explicitly) instead of `finished`, and the connection could not be reused. Whether this happened depended only on how the provider split its last bytes into chunks. The first consumer recording real Gemini exchanges, dash-crm's recorded agent tests, publishes only complete bodies, so recordings with a cut-off ending were refused.
- On 2026-11-18 the repository owner ruled that the caller receives the outcome only after the body has ended or the bound has passed, so nothing the call started outlives it. Progress already accepted is still delivered as it arrives; only the outcome waits.
- After a provider terminal, for any outcome decided at or after it (including a provider-reported failure and a tool batch refused by admission), the stream owner asks the transport worker to finish the body. The worker reads and discards the rest with HTTP Gun's bounded read, `body.next_within`, for at most 1 s, one deadline set when it starts, and 64 KiB, then leaves its HTTP Gun scope, which ends or closes the body synchronously, and only then reports to the owner, which delivers the outcome. The bound is not configurable. It is a chosen cap, not a measurement: no gap between a real provider's terminal event and the end of its body has been measured, and dash-crm's key-free contract case uses 500 ms. HTTP Gun's request deadline, which carries the whole-call and application deadlines, fails a pending bounded read, so both still cap the wait. Past the bound, on an oversize chunk or on a read failure, the worker closes the body before it reports and the outcome decided at the terminal stands. The owner keeps one backstop timer beyond the bound in case the worker does not answer. The bound includes HTTP Gun's recording writes, which it holds the body for.
- Bytes after the terminal never change the outcome. In the chunk that carries the terminal, the framer still frames them, but events after the terminal are dropped and a framing failure after it no longer replaces the outcome; otherwise the outcome would again depend on how the provider split its last bytes. For the same reason, events framed before a framing failure are now interpreted before it in every chunk, so their progress reaches the caller before the failure, as it would have had the failure arrived in a later chunk. Later chunks are never parsed. The whole-chunk size limits are the one exception: a chunk that carries the terminal and exceeds ChunkBytes or ResponseBodyBytes with its trailing bytes still fails, as a limit on what the provider sent. Failures found before the terminal (limits, malformed streams, generation timers) close the body at once, as before. Close and creator death request the close at once and do not wait for the body to end, as for any close: the ruling's "nothing outlives the call" holds for every call that is not cut short by its caller.
- Rejected: delivering the outcome at once and leaving the transport worker to finish reading after the call returned. It adds no latency, but part of the call outlives its return, and an HTTP Gun recording finished with no wait right after the call sees an exchange still in flight.
- Rejected: delivering the outcome at once while the owner keeps the body. The owner ends with its creating process, so a creating task that ends right after its turn, as dash-crm's agent runs do, still cuts the body off.
- Rejected: storing such an exchange as finished in HTTP Gun, or accepting a not-finished ending in the consumer. HTTP Gun cannot see a server-sent-event terminal, and its label is truthful: the body was cut off.
- Rejected: a bounded read to the end inside HTTP Gun, run when a body is closed or its scope is left early. Only the protocol layer knows that the rest of a body carries no meaning; for every other early close HTTP Gun's close is a cancellation and must stay immediate. HTTP Gun already provides the bounded read this needs, so LLM Wire composes it and duplicates no HTTP runtime; the bound is a property of server-sent-event responses, not of the HTTP client.
- No new observation reports a body closed at the bound. The observation outcome set is a closed public type, so a new outcome would break callers' exhaustive matches. The cut-off stays visible where it matters: an HTTP Gun recording stores that exchange with a cut-off ending, and the existing cleanup observation still marks the release.

## Evidence and limits

- This repository's own live cassettes show the defect is the common case, not an edge: of the ten in `test/cassettes/live/`, all seven Google recordings and `openai-union-no-sources.json` store a complete answer with the ending `aborted` (`cancelled`), and only `openai-union-written.json` and the buffered `typesafe-classification.json` end `finished`. They hold no timing that would measure the gap. Their offline replays still pass: a replayed cut-off ending ends the trailing read at once and the answer stands.
- Costs: every caller pays the wait, `run` and `collect` as well as stream readers, because the outcome itself waits. An outcome can arrive up to 1 s after the terminal event, and the connection stays occupied for that time, when a server is slow to end its body. A provider-reported failure decided at the terminal waits too, so each retry of it can gain up to the bound. A caller that reads with its own short budget and closes on expiry can lose, inside that window, an answer the provider completed. These follow from the ruling to deliver after the body ends.
- The benefit differs by protocol. A recording ends `finished` over HTTP/1.1 and HTTP/2 alike. Connection reuse is an HTTP/1.1 gain: an early close of an HTTP/2 stream cancels only that stream and leaves the connection usable.
- A provider that routinely exceeds the bound adds 1 s to every call with no dedicated signal. The `Terminal` observation marks the latch and `Cleanup` the release, so the time between them is the trailing read; an observer can measure it without a new outcome. A dedicated outcome is not worth a breaking change to the closed public outcome type until such a provider is seen.

- `test/llm_wire_stream_end_test.gleam` serves each built-in provider's answer from a local server, ends the chunked body 0, 50 and 500 ms after the terminal event, and records the exchange through HTTP Gun. Before this change Google at 50 ms was stored `abandoned`. The same file covers a body that never ends, trailing bytes and events, close during the read and connection reuse.
- A provider that routinely ends its body more than 1 s after its terminal event would still be recorded as cut off, visible only in HTTP Gun's recording or its own termination observation.
